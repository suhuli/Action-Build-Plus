1. 快速开始

这个项目不是在本地电脑上直接编译，而是让 GitHub Actions 在临时的 Ubuntu Runner 上完成源码同步、补丁处理、内核编译和产物上传。你只需要选择工作流参数并下载产物。

项目入口

打开 Action-Build-Plus → Actions → Build OnePlus Ace Race T Kernel → Run workflow。

FILE 选项已经固定为 oneplus_ace_race_t，不会显示其他机型。

  1. 打开 Actions 页面。第一次使用时，GitHub 可能要求确认启用 Actions。
  2. 选择 Build OnePlus Ace Race T Kernel。在右侧选择 Run workflow，确认 Branch 为 main。
  3. 按推荐配置填写参数。第一次建议不要同时打开 ZRAM、LZ4_UPDATE、DroidSpaces、Re-Kernel 等实验性选项。
  4. 等待 Job 完成。重点观察 Extract Manifest Info、Initialize Repo and Sync、Build Kernel FAST 和 Upload AnyKernel3。
  5. 下载构建产物。打开成功的运行记录，在页面底部 Artifacts 下载 AnyKernel3_...。如果开启了 ZRAM，可能还有单独的 ZRAM 模块产物。

第一次使用前的准备

  • 保存当前可开机的 boot 镜像、原厂 boot 或完整救砖方案。
  • 确认手机确实是 OnePlus Ace 竞速版，并确认当前系统与 Android 13 / T 清单匹配。
  • 不要把 GitHub Actions 的 Artifact ZIP 误当成普通 boot.img 直接使用；它是 AnyKernel3 刷入包的文件集合。
  • 构建成功只代表编译和打包成功，不能替代在目标手机上的刷入验证。

以下是最适合第一次构建的保守配置。用户已验证过的旧版构建曾使用 KPM=N/A 并成功刷机；升级版工作流的实际测试使用 KPM=KPM 编译成功，但是否适合你的日常刷入应单独验证。

3. 参数详解

工作流中的参数都会进入 GitHub Actions 的 github.event.inputs，随后写入环境变量或直接控制某个 Step 的 if 条件。参数名必须保持原样。

3.1 源码、版本和管理器

参数可选内容实际作用
FILE固定为 oneplus_ace_race_t决定使用哪份 manifest。此项目只保留 Ace 竞速版。
DYNAMIC_REPO默认 Numbersf只对动态清单路径有意义。Ace 竞速版优先走内置清单，不依赖这里查找。
BUILD_TIME时间字符串、F 或 -1写入内核版本时间。F 使用当前 UTC；自定义时间会影响版本识别和产物差异。
KSU_META四段格式格式为 管理器分支/内置分支/自定义标识/提交哈希。默认 main/builtin/Numbersf/ 表示管理器 main、内置层 builtin、无自定义标识、不回退提交。
SUFFIX空、普通字符串或 -1空值使用随机后缀；普通字符串写入内核版本；-1 关闭后缀修改。
RESUBLEVEL空或数字修改内核 Makefile 的 SUBLEVEL，用于处理系统升级后版本等级校验差异。

3.2 SUSFS、KPM 与产物组件

参数值含义
SUSFS_META空 / 数字 / Commit / -1空值使用当前分支最新版本；数字表示 HEAD~n；Commit 表示固定提交；-1 完全关闭 SUSFS 内核补丁。
SUSFS_CICI / Release / N/A决定是否把额外 SUSFS 模块 ZIP 放入 AnyKernel3。它与 SUSFS_META 是两个独立开关。
SUSFS_DEV布尔值为 true 时拉取 SUSFS-DEV 分支，适合开发测试，不建议日常使用。
KPMKPM / KPN / N/AKPM 使用 patch_linux；KPN 使用 kptools-linux 和 kpimg-linux；N/A 跳过最终 Image 的外部 KPX 注入。
ZRAM0/算法/大小 或 1/算法/大小第一段为开关，第二段为算法，第三段为字节数。当前工作流会尝试额外生成 zram 模块。
LZ4_UPDATE布尔值为 true 时额外拉取 Numbersf/lz4_oplus 并执行其上游脚本。

3.3 内核功能开关

4. 运行原理

可以把项目理解成一个“参数驱动的内核构建控制器”：仓库本身保存工作流和补丁工具，GitHub Actions 提供临时的 Linux 构建机，工作流根据输入拼装源码、配置和产物。

1. DispatchGitHub 记录 workflow_dispatch 输入和提交 SHA。
2. Runner创建 Ubuntu Runner，清理磁盘并准备交换空间。
3. Assets第二次 checkout 当前仓库，固定脚本、补丁和 ZRAM.zip。
4. Manifest为 Ace 竞速版写入内置 XML 清单。
5. Sourcerepo 根据清单同步 kernel、vendor 和预编译工具链。
6. Patch加入 SukiSU、SUSFS、FakePatch 和可选功能补丁。
7. Build识别 KMI、工具链和配置，执行快速编译。
8. Package找到 Image，替换 AnyKernel3/Image 并上传 Artifact。

4.1 为什么是 GitHub Actions

  • 工作流运行在 GitHub 提供的临时 Ubuntu Runner 上，不依赖本地 Windows 是否安装 Android 编译环境。
  • 每次运行都是相对干净的临时环境；真正持久化的只有 GitHub Actions Cache 和 Artifact。
  • 工作流使用 ccache、ThinLTO cache 和 APT cache 加速后续运行。第一次构建没有完整缓存，时间通常更长。
  • 磁盘扩容步骤必须先完成，构建资产 checkout 放在扩容之后，否则嵌套目录可能被重新挂载的工作区遮蔽。

5. 流水线分解

5.1 初始化与设备识别

Checkout 获取当前工作流代码；Maximize Build Space 扩大构建卷；Checkout Build Assets 将同一个仓库提交检出到 kernel_workspace/Action-Build。这样脚本和补丁不会随着上游默认分支的下一次更新突然改变。

Extract Manifest Info 对 Ace 竞速版直接生成清单。关键片段等价于：

kernel:  android_kernel_5.10_oneplus_mt6895
branch:  oneplus/mt6895_t_13.0.0_ace_racing
vendor:  android_vendor_mediatek_kernel_modules_mt6895
build:   ./kernel_platform/oplus/build/oplus_build_kernel.sh unknown gki

工作流随后从 manifest 的 revision 中提取：

  • CPU=mt6895，决定 MTK 分支和部分补丁条件。
  • ANDROID_VERSION=13.0.0，用于设备/系统版本和 Artifact 命名。
  • CPUD=unknown、BUILD_METHOD=gki，用于官方脚本回退路径。

5.2 KMI 与内核版本

手机系统 Android 版本和内核的 GKI/KMI 版本不是同一个字段。Ace 竞速版清单是 Android 13，但该内核在实际构建日志中可能识别为 android12-5.10 的 KMI，最终 Artifact 则同时显示设备 Android 版本和真实内核版本，例如：

AnyKernel3_SukiSUUltra_41503_OnePlusAceRace_Android13.0.0(5.10.110)_BBG_ILH

其中 Android13.0.0 来自设备清单，5.10.110 来自内核 Makefile，BBG 表示启用 BBG，ILH 是当前上游产物命名中的固定标识。

5.3 缓存与依赖

工作流会尝试恢复三类缓存：

APT Cache

缓存编译依赖包，减少 apt 下载时间。

ccache

缓存编译器输出，同一源码和工具链第二次通常明显更快。

ThinLTO

极速构建模式下缓存 ThinLTO 中间结果。

缓存命中不代表可以跳过源码同步。工作流仍会初始化 repo，缓存只减少重复下载和编译。

5.4 补丁顺序

  1. 根据 SUSFS_META 获取对应 SUSFS 源码，并应用 FakePatch。
  2. 调用 SukiSU-Ultra 的 setup.sh，加入 KernelSU/SukiSU 层。
  3. 应用 SUSFS kernel patch、文件系统修改和头文件修改。
  4. 按输入应用 NTSYNC、DroidSpaces、Unicode Bypass、Re-Kernel、ZRAM、LZ4 和 HMBIRD 等可选功能。
  5. 运行 reject 检查器，发现 patch 产生的 .rej 文件时报告问题。

为什么不要一次开启所有选项

补丁不是完全独立的。它们可能共同修改 KABI、Kconfig、fs 或内核版本脚本。一个选项单独成功，不代表多个选项叠加后仍能启动。排查时应一次只改变一个变量。

5.5 编译与镜像后处理

快速构建阶段会生成 gki_defconfig，按内核版本设置 LTO，然后显式启用：

CONFIG_SECCOMP=y
CONFIG_SECCOMP_FILTER=y

之后执行 olddefconfig 和并行 make。完成后工作流会寻找 Image，复制到 AnyKernel3 的 Image 路径；如果选择 KPM 或 KPN，还会在 Final-Image-Find 中对 Image 做对应处理。

6. Ace 竞速版设备清单

内置清单为什么重要

上游最新通用项目已经移除了 oneplus_ace_race_t 的通用选择项，但 Action-Build-Plus 保留了专用内置清单。因此不能直接用上游仓库覆盖本项目，否则会丢失这款手机的 manifest。

项目值说明
内核仓库android_kernel_5.10_oneplus_mt6895OnePlus MT6895 5.10 kernel。
内核分支oneplus/mt6895_t_13.0.0_ace_racingT 代表 Android 13 版本代号。
vendor modulesandroid_vendor_mediatek_kernel_modules_mt6895同一 Ace Racing 分支。

7. 产物与刷入

7.1 Artifact 内容

当前上游工作流的 Upload AnyKernel3 上传的是 AnyKernel3/ 目录内容。GitHub 下载时会再包装成一个 Artifact ZIP，所以下载文件名和内核刷入包显示名可能不同。

主产物

AnyKernel3_SukiSUUltra_...
包含 AnyKernel3 脚本、Image、模块和配置。

可选产物

ZRAM-Module_...
只有 ZRAM 开关为 1 且成功找到 zram.ko 时才上传。

7.2 建议的刷入流程

  1. 下载成功运行记录中的主 Artifact，并在电脑上保留原始下载文件。
  2. 确认产物名称中的设备、Android 版本和内核版本符合预期。
  3. 使用你已经验证过的 AnyKernel3 兼容刷入方式，例如 Kernel Flasher 或兼容的 Recovery/Root 工具。不要把整个 Artifact ZIP 当作普通 boot.img 通过 fastboot 直接刷入。
  4. 刷入前保存当前可开机 boot 镜像；首次尝试时不要同时安装额外 ZRAM 模块或其他实验模块。
  5. 刷入后等待首次启动，进入系统检查内核版本、Root 管理器和关键功能；出现 bootloop 时恢复原 boot。

重要边界

本文只解释构建系统，不替代针对具体 ROM、分区布局和 Root 方案的刷机教程。不同系统版本可能要求不同的 boot/init_boot/vendor_boot 处理方式。

8.1 如何看日志

  • Step success：该阶段退出码为 0，但仍可能打印 warning。
  • Step failure：该阶段退出码非 0，后续步骤通常会跳过。
  • continue-on-error：SUSFS 模块和管理器 APK 下载允许失败，主内核仍可能继续生成；需要检查 Artifact 是否包含对应附加文件。
  • Annotations：warning 不是失败。要先看对应 Step 是否为 success，再判断是否影响产物。

9. 可复现性与更新策略

当前项目已经把工作流脚本、补丁和工具资产 checkout 到本次仓库提交，避免“工作流不变但上游默认分支自动变化”。不过源码和部分外部组件仍然具有动态性。

内容当前固定程度影响
本仓库工作流、scripts、patches、lib固定到 GitHub Actions 触发时的提交 SHA同一个提交可以复查。
Ace kernel 分支manifest 指定分支名远端分支以后移动时，重新运行可能得到不同源码。
CodeLinaro 工具多数使用固定 revision相对稳定。
SUSFSSUSFS_META 为空时使用最新分支同样输入在不同日期可能得到不同 patch；排查时使用 Commit 或数字回退。
SukiSU managerKSU_META 默认 main/builtin/Numbersf管理器层可能随分支更新；需要固定时填写对应 commit。
ccache / ThinLTO由 Actions Cache 保存缓存可加速，但不应当被视为源码版本证明。

推荐的升级方法

先从上游同步到独立分支，保留内置 Ace manifest，完成 YAML/actionlint 检查，再用 KPM/N/A 的最小配置构建。编译成功后刷入验证，最后才更新 main。不要直接覆盖主工作流，也不要删除内置清单。

11. 术语表

GKI / KMI

GKI 是 Generic Kernel Image；KMI 是内核模块接口/版本组合。Android 13 手机并不意味着日志里的 KMI 一定写 Android 13，Ace 竞速版的 5.10 构建可能显示 android12-5.10。

AnyKernel3

一种通过脚本在设备上识别分区并替换内核 Image 的刷入结构。它不是单一的 boot.img。

KPM / KPN

两种对最终 Image 做内核模块能力处理的路径。KPM 使用 patch_linux，KPN 使用 kpimg 与 kptools。

SUSFS

内核侧隐藏、状态伪装和文件系统相关能力集合。SUSFS_META 控制内核 patch，SUSFS_CI 控制附加模块下载。

FakePatch

为了兼容不同内核 SUBLEVEL 和 SUSFS，在正式应用 patch 前临时调整代码、完成后再恢复的处理逻辑。

ccache / ThinLTO

前者缓存编译器结果，后者缓存 ThinLTO 中间结果。它们只影响速度，不改变设备清单。

一句话总结

Action-Build-Plus 先用内置 manifest 找到 Ace 竞速版的 MT6895 5.10 源码，再按输入加入 SukiSU/SUSFS 和可选补丁，利用 GitHub Runner 完成 GKI 编译，最后把 Image 放进 AnyKernel3 并上传；设备能否开机最终仍以实际刷入验证为准。

文档对应仓库：suhuli/Action-Build-Plus。项目工作流、上游依赖和设备源码可能变化，遇到冲突时以 GitHub Actions 的实时日志为准。
